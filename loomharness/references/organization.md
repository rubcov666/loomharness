# Постоянные направления, независимая приёмка и выпуск

## Первый запуск

Исходи из цели, материалов и задач конкретного проекта. Направлением может быть исследование, набор данных, закупки, редактура или раздел приложения. Закрепляй постоянного владельца там, где ожидаются несколько связанных поручений. Чат появляется при первой выдаче. Разовую задачу с готовыми входами можно выполнить в текущем чате или поручить запрошенному временному помощнику.

При первом планировании спроси, нужен ли Git, если ответ ещё не дан. Если Git не нужен или пользователь выбрал работу без репозитория, сохрани `--git none`. Для имеющейся рабочей копии используй `--git existing` и при необходимости `--git-dir`. Создание репозитория — отдельное поручение. Спроси о месте передачи готового результата, когда это влияет на ближайший выпуск. Для документа им может быть папка, для данных — хранилище, для приложения — конкретная среда.

Главный чат выполняет `team.py intake`, при отсутствии доски создаёт её через `init --mode roles` с целью и двумя доступными моделями. Затем выполняет `team.py organize owners.json --slots 2 --git none` с фактическим выбором пользователя. Формат owners.json — объект, в котором ключом служит название направления, а значением — краткая область ответственности. Для передачи JSON через stdin используй `organize -`. Для изменения состава повтори organize в перерыве между назначениями, сохранив названия прежних направлений. Два рабочих места — исходная настройка для первых независимых поручений; количество можно менять. Проверяющий и ответственный за выпуск имеют отдельные места.

## Координатор

Когда владелец просит самостоятельно доводить проект до готовности и предлагать улучшения, включи [обзор направлений и выбор результата этапа](initiative.md). Сводка доски показывает занятые места, следующие поручения, очередь ревью, служебные задания и вопрос владельцу. Для состава команды есть `inbox --roster` со своим курсором. Для подробностей этапа доступны `pulse`, `plan` и `show ID`.

Для наблюдения за командой вызови `team.py inbox --watch`. Если ведёшь конкретную карточку, добавь `--card ID` в тот же вызов. Поле `card` соответствует `show ID` и читается вместе с доской в одной транзакции. Сохраняй полный ответ и его курсор. Повторяй те же параметры с `--after КУРСОР`. При `{"changed":false}` используй последние данные и курсор. Если потерял сохранённый ответ, запроси его заново.

Если карточка содержит длинные доказательства или часто меняются соседние задачи, выбери `inbox --watch --card ID --parts`. Первый ответ содержит `board`, `card` и один курсор для обеих частей. В этом режиме цели ожидания находятся в `board.watch`. При обновлении с `--after` замени каждую полученную часть целиком, сохрани прежнее значение пропущенной и затем запомни новый курсор. При `changed: false` всё сохранённое остаётся актуальным. Если после возобновления чата недостаёт любой части, запроси обе без `--after`.

Из `watch.targets` возьми идентификаторы чатов для `wait_threads`, сопоставь с известным хостом и последним курсором Desktop каждого чата. Поле `assignment` сохрани рядом с отправляемой целью. Обрабатывай первое завершение, ошибку или запрос ввода. При большом числе исполнителей чередуй группы в пределах доступного лимита инструмента и ближайшего срока.

При передаче поручения сохрани правило из `brief.on_blocker`. Если исполнителю недостаёт исходных данных или нужно согласовать пересечение работ, он выполняет доступную часть и завершает ход сообщением координатору. Прочти его итог, проверь доступные источники, согласуй границы задач и верни решение исполнителю. К владельцу обращайся из чата координатора, когда только он может предоставить необходимый доступ, разрешение или выбрать результат. Системные запросы разрешений обрабатывает сам владелец.

Только после обработки результата `idle` с завершённым ходом `completed` передавай в следующие вызовы `inbox --watch` пару `--settled ASSIGNMENT ВРЕМЯ` для этого поручения. Время — Unix-секунды при получении ответа. До следующей сверки сохраняй исходное значение. Для нескольких чатов повтори параметр. После нового сообщения в чат, ошибки, запроса разрешения или возобновления сбрось его отметку и сразу обработай событие. Новый билет или этап возвращает чат в очередь автоматически. Если ход завершён, а работа ещё числится активной, один раз сверь сдачу или выясни препятствие.

`watch.recheck_at` задаёт ближайшую контрольную сверку в Unix-секундах, максимум через 30 секунд от отметки. Ограничь ожидание других чатов этим сроком. Если все текущие поручения временно исключены, используй `inbox` с теми же параметрами, `--after КУРСОР --wait 30`. Изменение доски, файл остановки и истечение отметки видны при этом ожидании. Без активной работы и ожидаемых решений заверши цикл. Сообщение владельца и новые запросы доступа обрабатывай при поступлении.

В программном цикле обрабатывай ответ Desktop один раз. Отметки после доставки событий обновляет готовый фрагмент [scripts/record_wait.js](../scripts/record_wait.js): прочти его и передай `reply`, `sent`, `settled` и время получения в секундах. `sent` содержит записи из `watch.targets`, выбранные для конкретного ожидания. `settled` хранит пары для текущего проекта и чата координатора. Отбрось ответ старого ожидания, если во время него отправлено новое поручение.

Сохраняй курсоры Desktop отдельно от курсора доски. Удаляй истекшие отметки и отметку перед новой отправкой в тот же чат.

1. Получив поручение, сверь смысл, границы и критерий с уже известным составом команды. Назначь одного ответственного. Если есть независимые части, заведи отдельные карточки с зависимостями. При конфликтующих требованиях уточни только решение владельца. Координатор ведёт очередь и не забирает реализацию и ревью себе.
2. В `add`/ `edit` укажи точное имя роли через `--role` и общие области записи через повторяемый `--resource`. Используй один канонический ключ на общий файл, сервис или набор данных во всех заданиях. Ключи совпадают целиком, каталоги и вложенные пути сами не сопоставляются. При неизвестном пересечении опусти ключи у новой карточки — тогда она займёт весь проект на время исполнения. Изолируй рабочие результаты или используй неизменяемые версии при параллельной работе. Учти инструменты, которые пишут в общий каталог сборки или кэш.
3. Выдай доступные карточки через `dispatch ID`. Используй возвращённые поля — operation, threadId, model, thinking и brief с кратким поручением для Desktop (контракт полей — в team.md). Новый чат регистрируй через `bind`, повторное поручение уходит владельцу направления. В ходе работы принимай новые сообщения пользователя, добавляй карточки и сразу выдавай готовые при свободном месте. Когда мест нет, сохрани карточку в очереди. Ожидай события `wait_threads` по активным ID с курсорами, обрабатывай первое завершение или новый ввод. Локальная доска хранит состояние; дальнейшие назначения выполняет активный чат Codex.
4. Исполнитель начинает через `claim` и передаёт результат через `submit ID БИЛЕТ "результат и доказательство" --revision ХЕШ`. Для Git подходит полный ID доступного коммита. Для любых файлов подходит SHA-256 неизменяемой копии, при нескольких файлах — архива результата. Укажи `--artifact относительный/путь` от корня общей доски. Версия должна содержать именно то, что предстоит принять и передать. Для работы с сервисом сохрани версионированный экспорт или проверяемую запись результата и опиши, как сверить её с реальным объектом.

Для формального этапа передай при выдаче `--stage bounded --work-type ТИП`. Доска подставляет быструю модель только для типа работы, прошедшего сравнение с основной. При неопределённой причине выбери `diagnosis`. Между этапами одной карточки используй `next-stage`. Порядок сравнения моделей и фонового ревью приведён в [инструкции для координатора и ревьюера](adaptive-team.md).

Дальнейшие этапы вынесены в отдельные файлы, чтобы читать только нужный сценарий: независимая приёмка — в [review.md](review.md), подготовка и публикация выпуска — в [delivery.md](delivery.md). Краткий порядок исполнителя — в [executor.md](executor.md).
