# Выбор модели и работа ревьюера во время теста

Команды ниже выполняются через установленный `scripts/team.py --project ПАПКА` из чата соответствующей роли. Доска хранит решения отдельно для каждого проекта.

## Один ревьюер и фоновый тест

1. Исполнитель, у которого для приёмки достаточно короткой проверки зафиксированных входов, добавляет `--quick-review` к `submit`. Куратор при создании задач указывает конкретные ключи общих ресурсов через `--resource`. Пересекающиеся и неизвестные области требуют отдельного времени. Долгий сетевой запрос, новая сборка или действия с работающим сервисом для короткой проверки не подходят.
2. Ревьюер берёт обычный `job-claim`, сверяет точную версию и самостоятельно выбирает проверку. Долгий тест запускает через `review-test --recheck 300 JOB БИЛЕТ КАРТОЧКА -- ПРОГРАММА АРГУМЕНТЫ`. Передай аргументы списком. Код 0 означает, что все критерии этой проверки выполнены. Обёртка работает в корне проекта, отдаёт вывод процесса и записывает исход на доску. Используй фоновую сессию обычного инструмента и сохрани её идентификатор.
3. В `inbox --watch` (для `--parts` внутри `board`) активное задание ревьюера содержит `test` и, когда есть подходящие карточки, `short_ready`. Куратор выбирает одну подходящую по длительности, выполняет `review-side JOB КАРТОЧКА` и передаёт полученный brief тому же чату ревьюера. Билет остаётся прежним. Для общего задания указывай `--task ID` в каждом отдельном вердикте. Если карточка потеряла актуальность между чтением и назначением, обнови снимок.
4. На время теста жди изменения доски через `inbox --watch --after КУРСОР --wait СЕКУНДЫ`, учитывая новые сообщения чатов и ближайший `watch.recheck_at`. Используй один снимок на цикл выдачи. Как только `test.status` стал `passed` или `failed`, верни внимание к исходной карточке. Для `passed` ревьюер проверяет доказательство и выносит независимый вердикт. Для `failed` виден код выхода, можно вернуть работу или повторить корректную проверку. Сбой блокирует одобрение исходной карточки.
5. При `check` пора сверить состояние сессии. Срок сверки сам по себе не означает сбой процесса. Если он подтверждённо остановлен, а результат не записан, ревьюер или куратор выполняет `review-interrupt JOB БИЛЕТ RUN "подтверждение остановки"`. Запоздалый результат прежнего запуска не влияет на повторный тест.

## Выбор модели для этапа

* Для этапа с известными входами и проверяемым ответом используй `dispatch ID --stage bounded --work-type ТИП`. Имена типов выбирай по выполняемой операции и её критериям качества. Например, извлечение полей и поиск причины расхождения требуют разных проверок.
* На согласованной границе работы в том же чате выполни `next-stage ID --stage bounded|standard|diagnosis|waiting`. Для новой операции добавь `--work-type ТИП`. Передай исполнителю следующий шаг с возвращёнными `threadId`, `model` и `thinking`. При `waiting` доска предлагает дождаться события. Текущая версия, исполнитель, ресурсы и билет сохраняются. Время работы внешнего теста и время в очереди оценивай отдельно от работы модели.
* При задержке прочитай последнее событие исполнителя. Если идёт внешний процесс, дождись его исхода. Если приходится заново искать причину или результаты противоречат друг другу, переведи следующий этап в `diagnosis`. Если осталась формальная операция с известным критерием, передай её как `bounded` с подходящим типом. Используй ровно ту модель, которую вернула доска.
* `standard` получает основную модель, `diagnosis` и повторный возврат после двух неудачных попыток получают сильную. Основная модель ведёт формальную работу до допуска быстрой. После возврата формальная карточка также переходит на основную. Возврат результата, в котором участвовала допущенная быстрая модель, отзывает допуск для соответствующей пары моделей и типа работ. Качество проверяет сильный независимый ревьюер.

## Сравнение на исторических задачах

1. В `.codex/harness-models.json` укажи кандидатуру быстрой модели, например `{"routine":"имя-модели"}`. Основная модель задана в проекте как `--simple-model`. Сравнение выполняют при проверке нового типа или смене модели. Обычная выдача карточки не запускает дополнительные чаты.
2. Куратор готовит примеры принятых и возвращённых версий с известными ошибками и пограничными случаями. Для каждого сделай нейтрально названный неизменяемый файл внутри проекта с задачей, исходными материалами и критериями. Удали старый вердикт, готовый ответ и подсказки из имени. В закрытом манифесте перечисли реальные пары задания ревью и карточки:

   ```json
   [{"job":21,"task":5,"input":"evaluation/sample-a.txt"},{"job":24,"task":6,"input":"evaluation/sample-b.txt"}]
   ```

3. `model-pack ТИП МАНИФЕСТ.json` возвращает две модели и случайные коды примеров. Для обеих моделей используй одинаковое задание и low. В первом сообщении каждого примера передай только его вход, задачу и метку `eval:КОД:SHA256`. Например, попроси исполнителя выполнить сверку и указать, соответствует ли исходный материал критериям. Для плеч сравнения используй разные авторизованные чаты с одинаковым доступом к входам и без истории старого решения. Сохрани фактические выходные файлы. Включи переделки до принятого результата в непрерывный диапазон ходов по этому примеру.
4. Независимый ревьюер сначала оценивает каждый результат по исходным критериям вслепую. Только затем связывает результаты с моделями для подсчёта. В JSON верхний ключ — точное имя модели, следующий — код примера. Для каждой пары укажи:

   ```json
   {"input_sha256":"…","output":"evaluation/answer-a.txt","output_sha256":"…","decision":"changes","quality_pass":true,"thread":"ID чата","first_turn":"ID первого хода","last_turn":"ID последнего хода"}
   ```

   `decision` — вывод о соответствии исходной версии (`approve` или `changes`). `quality_pass` — оценка полноты и правильности реально выполненного задания, включая найденную причину дефекта, когда этого требует критерий. Время и токены вычисляются из локальных журналов Codex. Время включает промежуток от первого запроса до завершения последнего хода, а токены включают вход и выход всех ходов диапазона.

5. Ревьюер вызывает `model-score НОМЕР_ПАКЕТА РЕЗУЛЬТАТЫ.json`. Обе модели должны выполнить весь набор и совпасть с независимой оценкой по каждому примеру. Для допуска быстрая модель также должна сократить суммарное время и уложиться в расход токенов основной модели. Неполная телеметрия, чужая модель, изменившийся файл или повторный учёт ходов прерывают оценку. `model-status` показывает куратору решения проекта. Для повторного допуска после регрессии подготовь новый пакет с этим случаем.
