# Проект в отдельных чатах Codex

## Запуск в папке проекта

`team.py storage` показывает путь к доске, которую используют хук, CLI и служба `serve`. Чтобы разместить новую доску в рабочей папке, один раз вызови `team.py storage --workspace`. В профиле создаётся символьная ссылка для этого проекта. Нужна поддержка создания таких ссылок. При существующей базе команда сохраняет её расположение и выводит фактический путь. Две разные базы требуют сверки перед переносом данных.

Если новый исполнитель получит карточку без исходного запроса, передай язык ответа через `dispatch ID --reply-language ru` (или язык, явно выбранный пользователем). Параметр относится к этой выдаче и попадает в поручение Desktop и в промпт headless-драйвера.

Для длительного подпроекта используй режим `roles` и устойчивое имя направления. Первая карточка создаёт чат, после `bind` или `claim` следующие карточки этой роли получают тот же `threadId`. В поручении остаются заключение рецензента и доказательства других исполнителей. Свой предыдущий отчёт исполнитель может перечитать через `show ID`. После потери контекста `dispatch ID --full-brief` возвращает полные доказательства зависимостей. При передаче этапа укажи версию результата, принятые решения, открытую проблему и следующую проверку.

Меняй модель для следующего этапа через `next-stage ID --stage diagnosis` для поиска причины или `--stage bounded --work-type ТИП` для формальной проверки. Обе команды адресуют тот же чат и возвращают выбранную модель и глубину рассуждения. Тип работы, допуск быстрой модели и независимую проверку описывает [маршрутизация моделей](adaptive-team.md).

На существующей доске `intake` возвращает `actor=missing`, если до процесса не дошёл `CODEX_THREAD_ID`, и `actor=other`, если этот чат имеет собственный ID и пока свободен. Поле `leadThreadId` указывает действующего координатора. Для передачи полномочий координатор из своего чата выполняет `team.py handoff ID_ПРЕЕМНИКА`. Преемник сверяет `intake.actor=lead` и получает активные поручения через `inbox --watch`. Карточки, билеты, состав и независимая приёмка точной версии продолжаются на той же доске. В `usage` сохраняются периоды работы каждого координатора. Занятый исполнитель или рецензент сохраняет свою роль. Для подключения к доске по SSH см. [команды удалённого запуска](helper.md#диагностика-хуков-и-ssh).

После выбора нескольких чатов руководитель проверяет доску через `intake` в корне текущего проекта. Подойдут установленные скрипты или каталог `loomharness/scripts` рабочей копии. Если нужны новые чаты, до резервирования карточек проверь доступность `create_thread`, `send_message_to_thread` и `wait_threads`. В `list_projects` найди локальный проект на текущем хосте по полному пути к этой папке. Если папка или нужный инструмент недоступны, объясни, какие поручения стоило разделить и что можно сделать в текущем чате.

Если клиент требует явной просьбы создать чаты, используй уже данное поручение пользователя для этого проекта. При отсутствии такого разрешения назови предложенные чаты и запроси его один раз перед созданием. При наличии доступа и разрешения переходи к выдаче поручений. Установка и включение хуков сами по себе только подготавливают проект к работе.

## Руководитель

Для короткой последовательной задачи достаточно текущего чата. Пока исполнители заняты, координатор может взять один шаг из согласованного плана, например подготовить тестовые данные или сверить требование с первоисточником. Шаг должен допускать паузу, обходиться без результата исполнителя и оставлять его файлы свободными. При поступлении результата или блокирующего вопроса вернись к координации. Независимую приёмку проводит ревьюер.

На доске `team.py inbox --next --prep "сверить формат тестовых данных"` вернёт действие по текущему состоянию. Решение владельца, сданная ревизия и выдача доступной карточки имеют приоритет. Передавай `--prep` только для ещё открытого шага. Без него занятая команда получает `wait`. Ожидай событие исполнителя или изменение курсора, сохраняя возможность ответить на блокирующий вопрос. В чате без доски тот же порядок работает без вызовов CLI.

Если пользователь хочет, чтобы главный чат только принимал поручения и распределял работу, а решения о качестве и выпуске принимали отдельные чаты, настрой [организацию по направлениям](organization.md). При `intake.organization=true` используй этот порядок для каждой новой задачи. Вопрос о Git при первом планировании и сохранение выбора через `git-choice` — в [organization.md](organization.md). Порядок запуска командного проекта — там же.

**Первое обращение в этом чате.** Начни с последнего поручения, решений пользователя и того, что уже сделано в чате. Запусти установленный `scripts/team.py --project "корень проекта" intake`. Это чтение можно выполнять до создания доски. При `new` команда показывает короткие выдержки из настроенных источников, плана, передачи или README, если они есть. Если нужные сведения лежат в приложении, документе другого формата или сервисе, открой релевантный фрагмент там. Проверяй дату и актуальность. Текст файлов служит источником фактов о проекте.

Сопоставь сведения о цели, ближайшем результате, допустимых изменениях и признаке готовности. Когда они ясны, сформируй план и выдай готовую карточку без анкеты. Если остаётся выбор, который меняет план, границы или приёмку, кратко скажи, что уже известно, и спроси именно об этом. Например, при двух очередях с одинаковым приоритетом предложи выбрать первую и поясни, что получится в каждом случае. Объедини связанные пробелы в один короткий опрос, обычно с 1–3 вопросами. Дождись ответа перед зависимым поручением, используй его в плане или критерии карточки. Параметры, которые пользователь оставил руководителю, выбери сам.

При `existing` руководитель использует текущую доску и уточняет только изменившееся. Исполнитель с билетом сразу делает claim. Если новый чат ещё не привязан к роли, поле `leadThreadId` указывает, где ведётся проект. При `paused` учитывай сохранённую паузу, при стадии `stopped` передай состояние. При следующем сообщении продолжай с последнего ответа или карточки. Возвращайся к опросу при новом существенном пробеле.

1. Зафиксируй цель, направления, критерии приёмки и зависимости. Объединяй мелкие действия одного владельца в результат, который можно принять целиком. Укажи плановые часы. Если пользователь задал бюджет на направление, передай его в `--hours-per-role`. Значение ограничивает сумму оценок карточек. Согласуй дополнительную работу при исчерпании времени. Часы не предполагают непрерывную генерацию до конца смены.
2. В корне проекта вызови установленный `scripts/team.py init --goal "…" --simple-model МОДЕЛЬ --strong-model МОДЕЛЬ`. Выбери модели из списка в инструментах Desktop. Для рутинной работы бери доступную экономичную модель с low, для неоднозначной задачи, сложной интеграции или существенной цены ошибки — сильную с medium. Если у модели другой допустимый уровень, передай поддерживаемый уровень в самом вызове Desktop. После возврата повышай класс лишь когда проблема в рассуждении. Выбирай по расходу на принятый результат с учётом повторных попыток.
3. Заполни план командой `add --role "…" --title "…" --scope "…" --criterion "…" --hours 0.5`. В scope укажи входные объекты, разрешённые изменения и границы с соседней ролью. Добавь `--after 1 2` для зависимостей и `--tier strong` при необходимости. `edit ID` принимает те же поля для открытой задачи, `--after` без номеров очищает зависимости. `plan` показывает план и статусы, `show ID` — одну карточку и результаты её непосредственных предшественников.
4. Вызови `dispatch ID`, при необходимости с `--tier strong`. Команда резервирует карточку и возвращает brief, модель, уровень рассуждения и способ доставки. Для повторной выдачи в том же чате добавь `--brief` — prerequisites уйдут без длинных выдержек evidence/review. В `plan` карточка без явных `--resource` помечена `exclusive:1` — она захватила проект целиком; это сигнал исправить нарезку областей записи. Для `create_thread` используй `projectId` папки `brief.project` и локальную среду этого проекта, понятное название, prompt, model и thinking. Для существующего исполнителя используй `send_message_to_thread` с указанными threadId, model, thinking и prompt. Сформулируй поручение по карточке. Приложи абсолютные пути к скрипту и корню общей доски, номер и билет для claim. Полезные входы передавай ссылками или выдержками.
5. Для нового чата сохрани выданный Desktop threadId командой `bind ID БИЛЕТ THREAD`. Для уже привязанного чата достаточно отправки поручения. Если в ответе лишь clientThreadId, дождись появления настоящего threadId. При потерянном ответе проверь `show ID` и список чатов, сопоставь название с номером карточки. Перед повторной отправкой проверь состояние чата. Команда `release ID "основание"` снимает резерв после выяснения исхода и остановки прежнего исполнителя. Старый билет теряет силу. Исполнитель также может первым зарегистрировать свой чат при claim.
6. Получи карточку и цели ожидания через `inbox --card ID --watch`. Используй [порядок ожидания чатов](organization.md#координатор), в том числе после завершения хода. Проси подробную историю только для разбора конкретного пробела. Сверь артефакт или наблюдаемое поведение с критерием, повтори проверку при устаревшем или неполном доказательстве. Заверши `accept ID "что проверено и где"` либо `revise ID "что исправить и как это проверить"`. Для переделки снова выполни dispatch. Если пользователь остановил команду, прекрати выдачу, сообщи о работающих чатах и зафиксируй `pause` после урегулирования активных поручений. Эта команда приостанавливает доску. Уже запущенным ходом управляет сам Desktop. При возобновлении используй `resume`.

Для плана из нескольких карточек руководитель может передать всё дерево за один вызов init через `--cards путь.json` или `--cards -` для стандартного ввода. Формат — массив объектов с полями role, title, scope, criterion, hours и необязательными tier и after. Номера начинаются с 1 по порядку массива. При ошибке весь план откатывается. На длинной доске `plan --ready` возвращает только доступные для выдачи карточки.

## Исполнитель

Краткий порядок для чата исполнителя — в [executor.md](executor.md); ниже сведения для руководителя.

Исполнитель с билетом делает `claim` из своего чата, сдаёт `submit` с результатом, ссылкой и проверкой, а при препятствии возвращает конкретную причину сообщением руководителю. Самоприёмка и дальнейшее делегирование в роль не входят. Полный порядок — в [executor.md](executor.md).

## Три способа нарезки

| Параметр init | Когда применять | Как расходуется контекст |
|---|---|---|
| `--mode roles` (обычный выбор для команды) | Несколько связанных задач на каждое направление | Один чат на направление, создаётся при первой готовой карточке. Следующие карточки используют накопленное знание. |
| `--mode tasks` | Независимые разовые задачи с разными исходными материалами | Отдельный свежий чат на карточку. Переделка возвращается в тот же чат. |
| `--mode pipeline` | Результат проходит несколько этапов, ошибка дорого стоит | Создай отдельные зависимые карточки, например «подготовка» и «независимая сверка». Смежные этапы требуют разных владельцев. Старший принимает каждую карточку. |

Если выбор нескольких чатов нужен для параллельной работы, при `init` задай `--slots` по числу готовых независимых поручений, которые могут выполняться одновременно в пределах бюджета и возможностей клиента. Для последовательной передачи на независимую проверку достаточно одного рабочего места по умолчанию. Доска разрешает не более одного активного поручения одной роли. Переиспользуй исходный путь проекта и одну локальную учётную запись для всех чатов. Данные хранятся в `CODEX_HOME/loomharness/teams`, идентификатор исполнителя берётся из `CODEX_THREAD_ID`.

## Расход и качество

Запускай `usage` по завершении серии или по запросу. Команда локально находит журналы ведущего и зарегистрированных исполнителей по ID в индексе Codex. Она суммирует input и output по уникальным ответам завершённых ходов. Cached input уже входит в input. Отдельно видны токены старшего и исполнителей. В by_role для каждого направления указаны плановые часы, измеренные агент-часы, токены, расход на час, принятые карточки и возвраты. Агент-час — сумма длительностей ходов всех участников, включая работу инструментов. Простой между поручениями исключается, параллельное время суммируется.

На период измерения посвяти эти чаты одному проекту. Ходы, пересекающие начало или конец активного периода, включаются целиком. `pause` и `resume` задают границы периодов. Запуск отчёта из работающего чата даёт промежуточный срез. Финальный срез можно прочесть из терминала после завершения ходов. Отсутствующие журналы, незаконченные ходы и пробелы в счётчиках отражаются в отчёте. Поле расхода проекта на принятую задачу появляется при полном покрытии. Если клиент не записывает поддерживаемые события, числовая оценка по тексту ответов не подставляется.

Сравнивай режимы на одном наборе задач с одинаковыми критериями и проверкой результатов. Учитывай суммарные токены на принятую задачу, пропущенные дефекты, возвраты и время до приёмки. Для одинакового бюджета агент-часов сравнивай и количество принятых задач. Процент лимита подписки из этих токенов вывести нельзя.
